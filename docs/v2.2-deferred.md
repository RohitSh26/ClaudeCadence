# v2.2 bundle — deferred items

This document is on the v2.2 review branch only. Don't merge it as-is — strip or move to BACKLOG when squashing.

Four items were intentionally left out of the v2.2 bundle. Each needs its own focused design pass rather than getting jammed into a wave.

## 1. Bug B — mid-stream interrupt

**What:** when the user submits prompt #2 before Claude finishes responding to prompt #1, Claude merges them and the conversation log has both. Cadence currently sees the merged response but doesn't cleanly attribute it to two distinct turns.

**Why deferred:** I started a fix in v1.9.4 with a look-ahead heuristic and it broke things — it misidentified system-reminder injections as mid-stream interrupts and bled responses across turn boundaries. The correct fix is queue-aware: peek at remaining FIFO entries, bound collection by the next-turn's `lowerBoundTs`. That needs careful synthetic-race testing against real transcripts before shipping.

**Estimate:** ~4 hours, with the bulk in writing reproductions.

**Where to start:** `cadence_hook.js` :: `firstAssistantTextAfter`, `waitForFirstAssistantTextAfter`. The graph-derived catch-up (`deriveCatchUpNodes`) actually handles a lot of this for free — the gap is when both prompts land in a single hook fire.

## 2. Renderer virtualization

**What:** the viewer rebuilds the full DOM on every 5s poll. At ~500 nodes this is fine. At 5,000+ nodes it stutters. At 50,000 the page locks for a second on each poll.

**Why deferred:** virtualization is non-trivial for a `<details>`-based timeline (open state must be preserved across re-renders, focus must not jump, the rail/marker SVG positions need recalc). The right approach is diff-based — keep nodes that haven't changed, swap only the changed ones. That's a significant refactor.

**Estimate:** ~6 hours.

**Mitigation in the meantime:** the time filter already exists, and 5,000 nodes is unusual outside long orchestrator sessions.

## 3. GitHub Pages demo

**What:** host the iter6 demo viewer with synthetic BloomList data at `https://rohitsh26.github.io/ClaudeCadence/` so prospective users can see the plugin working before installing.

**Why deferred:** requires enabling Pages in the GitHub repo settings (the user does that, not me from the CLI), and choosing a build approach (`docs/` folder or `gh-pages` branch). It's a 30-minute task once the user has decided the deployment strategy.

**Estimate:** ~30 min after a decision.

## 4. Full orchestrator response synthesis

**What:** v1.9.7's graph-derived capture recovers prompts that bypassed `UserPromptSubmit` in orchestrator mode. The companion piece — synthesizing Claude's response when `Stop` never fires — works for simple turns but is incomplete for multi-fork orchestrator turns where the response is interleaved with sub-agent dispatches.

**Why deferred:** the synthesis logic is correct for the simple case. The hard case is when the orchestrator dispatches 5 sub-agents and the response is "I've dispatched these and will report back" + later "here's what they all returned" — currently we get the first part but the synthesis cluster boundaries aren't quite right.

**Estimate:** ~3 hours, mostly transcript-shape investigation.

**Where to start:** `cadence_hook.js` :: `deriveCatchUpNodes` — the response cluster collection that runs after a prompt is identified.
